# aicomply 2.3.0

Release notes for `@opena2a/aicomply` 2.3.0, against 2.2.3. The 2.2.3 figures and
outputs below come from the published 2.2.3 package and the 2.3.0 ones from this
tree, both run under Node.js v26.12.0.

## Exit code change: no input exits 2

`aicomply scan` now exits `2` with a `no input` message when the input is 0 bytes.
2.2.3 reported `CLEAN` and exited `0` for the same input.

| Input | 2.2.3 | 2.3.0 |
| --- | --- | --- |
| An empty file | `CLEAN`, exit 0 | `aicomply: no input: <file> is 0 bytes`, exit 2 |
| Empty stdin | `CLEAN`, exit 0 | `aicomply: no input: (stdin) delivered 0 bytes`, exit 2 |
| `git diff --cached` with nothing staged | `CLEAN`, exit 0 | `aicomply: no input: (stdin) delivered 0 bytes`, exit 2 |

A 0-byte file named beside a non-empty one does not decide the exit code: the
result is that of the non-empty file. The report lists the 0-byte file as
`EMPTY`, and `--json` gives it the same word, `"verdict": "EMPTY"`.

A gate written as `scan -q || echo "..."` now takes its failure branch when nothing
is staged. To fail on findings only, test for exit `1`:

```bash
git diff --cached | npx @opena2a/aicomply scan -q; [ $? -eq 1 ] && echo "staged changes not cleared"
```

[docs/commands.md](https://github.com/opena2a-org/aicomply/blob/main/docs/commands.md#exit-codes)
lists the exit codes.

## Library calls that now throw a TypeError

For JavaScript callers, these first arguments to `comply()` and
`ClassificationSession.comply()` are rejected with a `TypeError` in 2.3.0. The
number, array, `Buffer`, typed array and boxed `String` rows returned `CLEAN` on
2.2.3. The `Buffer`, typed array and boxed `String` calls held
the text `My SSN is 123-45-6789.` and got `CLEAN` from both functions on 2.2.3.
On 2.2.3 a `policyPack` on the first argument applied the default pack, whatever
its value.

| First argument | 2.2.3 | 2.3.0 |
| --- | --- | --- |
| `session.comply(123)` | `CLEAN` | `comply: expected a string or an options object like comply({ content: '...' }), got number` |
| `session.comply(['text'])` | `CLEAN` | `comply: expected a string or an options object like comply({ content: '...' }), got array` |
| A `Buffer`, on `comply()` or `session.comply()` | `CLEAN` | `comply: expected a string or an options object like comply({ content: '...' }), got Buffer` |
| A typed array such as a `Uint8Array`, on either | `CLEAN` | `comply: expected a string or an options object like comply({ content: '...' }), got Uint8Array` |
| A boxed string, `new String('...')`, on either | `CLEAN` | `comply: expected a string or an options object like comply({ content: '...' }), got String object` |
| `{ content, policyPack: 'hipaa' }`, on either | The default pack's result: `CLEAN` for `hello world`, `DENY [SSN, POLICY_DENY:pii-ssn]` for `My SSN is 123-45-6789.` | `comply: options.policyPack must name a built-in pack ('default'), got "hipaa". Pass a pack object on the second argument: comply({ content }, { policyPack })` |
| `{ content, policyPack: <pack object> }`, on either | The default pack's result: `CLEAN` for `hello world`, `DENY [SSN, POLICY_DENY:pii-ssn]` for `My SSN is 123-45-6789.` | `comply: options.policyPack must name a built-in pack ('default'), got object. Pass a pack object on the second argument: comply({ content }, { policyPack })` |

`comply(123)` and `comply(['text'])` threw the same `TypeError` on 2.2.3.
Pass text as a string, or as `content` on an options object, and pass a pack
object as `policyPack` on the second argument:
[docs/policy-packs.md](https://github.com/opena2a-org/aicomply/blob/main/docs/policy-packs.md).

## CLI

- A finding's value is printed as `•••`, with no characters of the detected
  value. 2.2.3 printed `123-•••89` for the SSN `123-45-6789`. The `--json`
  `maskedValue` field changed the same way.
- Each finding is printed with its line and column in the original input
  (`line 1 col 13`).
- `--json` adds `bytes` and `layers` to each source, and `line` and `column` to
  each finding.
- `--` ends the options, so a file name that starts with `-` can follow it.
  2.2.3 stopped with `aicomply: unknown option '--'`. An option written after
  `--`, such as the `-q` of `aicomply scan -- -notes.txt -q`, is read as a file
  name; when no such file exists, the message says
  `after -- every argument is an input; put -q before --`.
- A file without read permission gets `cannot read '<file>': permission denied`.
  2.2.3 printed `cannot read '<file>' (check the path)`.
- A file of 2 GiB or more gets
  `cannot read '<file>': it is 2 GiB or larger, and this CLI reads files under 2 GiB`,
  and a smaller file too large to decode as one input, such as 629145600 bytes
  decoded as UTF-8, gets
  `cannot scan '<file>': at <n> bytes it is too large to decode as one input`.
  2.2.3 printed `cannot read '<file>' (check the path)` for both.
- Input on stdin decoded as UTF-8, UTF-16 or UTF-32 and too large to decode as
  one input, such as 629145600 bytes decoded as UTF-8, gets
  `cannot scan (stdin): at <n> bytes it is too large to decode as one input`.
- The report lists at most 50 findings of an input. When an input has more, one
  line after them counts the rest by type, such as
  `... 49950 more (SSN 49950); use --json for all`. 2.2.3 printed one line for
  each finding: 50,009 lines for a file of 50,000 SSN lines. `--json` lists every
  finding.
- `--json` with `--quiet` prints the JSON report, as 2.2.3 did, and now also a
  line on stderr that says `--json` takes precedence over `--quiet`.
- Input that starts with a UTF-16 or UTF-32 byte order mark is decoded in that
  encoding. 2.2.3 printed `CLEAN` for a UTF-16LE file and for a UTF-32BE file
  holding an SSN; 2.3.0 prints `VIOLATION` and exits 1 for both.
- A directory argument gets its own message, which names the directory and
  shows a file glob to scan instead. 2.2.3 printed
  `cannot read '<dir>' (check the path)`.
- When files are named and stdin is piped as well, stdin is left unread and a
  line on stderr says so; add `-` to scan stdin beside the files.
- A `CLEAN` result reads `no findings from the layers that ran`, where 2.2.3
  read `safe to forward`.
- An input on which the regex engine could not run a pattern is reported
  `VIOLATION`, with a `PATTERN_NOT_EVALUATED:<id>` finding and a
  `not evaluated: <id>` line in the report; `--json` lists the pattern ids in
  `unevaluatedPatterns`.

## Large inputs

| Input | 2.2.3 | 2.3.0 |
| --- | --- | --- |
| 18,500,020 bytes, one SSN and one spaced card number on each line | stopped after 10 minutes without a verdict | `VIOLATION`, exit 1, 1.94 s |
| 81,397,690 bytes of text holding 55 SSN lines | `JavaScript heap out of memory`, exit 134, after 12.31 s at a 4.5 GB peak resident set | `VIOLATION`, exit 1, 2.09 s at a 473 MB peak resident set |
| 6,000,000 bytes of the letter `a` | `aicomply: Maximum call stack size exceeded`, exit 2 | `CLEAN`, exit 0, 0.18 s |
| 157,286,399 bytes of the letter `a` | `aicomply: Invalid array length`, exit 2 | `CLEAN`, exit 0, 2.35 s |
| 268,435,457 bytes: 134,217,729 copies of the digit `1`, one space between each two | `aicomply: Invalid array length`, exit 2 | `CLEAN`, exit 0, 11.47 s |

Each file was scanned with `aicomply scan -q` on one shared machine; the times
are single runs. The 2.2.3 results for the two files of the letter `a` and the
file of the digit `1` come from the source at the `v2.2.3` tag, built and run
with the 2.3.0 dependencies, not from the published package. Three runs of 2.3.0
on the file of the digit `1` took 11.47 s, 16.96 s and 37.04 s; the table gives
the fastest.

## Policy packs that 2.3.0 rejects

`comply()` and `classifyDualLayer()` reject the policy packs in the table with
a `TypeError`; 2.2.3 returned a result for each. A row gives the value passed
as `policyPack`, or what was changed in the pack below, which both versions
apply as `DENY [SSN, POLICY_DENY:r]`. A result is shown as its verdict and the
types of its violations.

```js
const policyPack = {
  name: 'p',
  version: '1',
  rules: [{ id: 'r', name: 'R', action: 'DENY', patterns: ['SSN'] }],
};
await comply({ content: 'My SSN is 123-45-6789.', useGuard: false }, { policyPack });
```

2.2.3 does not read `useGuard`; no Guard daemon was listening when it ran.

| Pack | 2.2.3 | 2.3.0 |

| `false` | `VIOLATION [SSN]` | `comply: dualLayerOptions.policyPack is not a valid policy pack: Policy pack must be an object (got boolean)` |

## Library

- `comply()` accepts `useGuard: false`, which makes no request to the Guard
  daemon address and returns a regex-only result.
- `comply()` accepts `guardOptions.baseUrl` to reach a Guard daemon on another
  address. An address that does not answer falls back to regex-only.
- `onRegistryUnknown: 'violation' | 'deny'` raises the verdict when the Registry
  cannot vouch for `sourcePackage`. With `sourcePackage: 'express'`, no
  `registryCache` and `onRegistryUnknown: 'deny'`, 2.3.0 returns `DENY` with a
  `REGISTRY_UNKNOWN` violation; 2.2.3 does not read the option and returns
  `CLEAN`.
- `registrySignals.status` reports the Registry lookup as `hit`, `miss` or
  `error`.
- A package with an alert in the loaded supply-chain alert list is a `hit` and
  gets `DENY` with a `SUPPLY_CHAIN_ALERT` violation and `supplyChainBlock: true`,
  also when the fleet index did not load. 2.2.3 returned `CLEAN` with
  `supplyChainBlock: false` for the same package, because its lookup returned
  `error` before it read the alert list.
- The supply-chain hard block reports `partial` when the alert page it holds is
  incomplete for the package asked about, instead of an empty alert list.
- `ClassificationSession.create()`, `warmRegistryCache()` and
  `new RegistryIntelligenceCache()` take a `sourcePackages` option, a list of
  `{ name, type }`. Warming the cache sends one fleet anomaly-signal request
  for each listed package, with its name and type in the query. A listed
  package the Registry reports fleet events for is a `hit`, and the fleet
  anomaly threshold applies to it; one it reports no events for is a `miss`
  when it has no supply-chain alert.
- `addSourcePackages()` on a session or a cache lists packages first seen
  later, in the same form, sends their fleet requests and resolves once each
  has been answered or has failed. A package listed already is not requested
  again.
- The result carries `pack` (the pattern pack's `version` and `sha256`) and
  `layers` (the layers that ran, for example `["normalize", "regex"]`).
- A regex finding's `value` reveals no leading characters: a value of 8
  characters or fewer is fully starred, one of 9 to 12 characters reads `...`
  and its last 2, and one of 13 or more `...` and its last 4. For
  `Passport: A123456`, 2.2.3 returns `A123...56` and 2.3.0 returns `*******`.
- Every counted repeat in the pattern pack has an upper bound. The pack loader
  of each runtime refuses a pattern with a counted repeat that has no upper
  bound, with a count above 1000, or with `{,m}` or `{,}`, which Python reads
  as a counted repeat and JavaScript as text, and names the pattern.
- A token run longer than 1000 characters is matched up to its 1000th
  character, and the env-var reference check, the `api_key=` pattern's
  validator and the removal of duplicate matches judge the captured value,
  which ends there; 2.2.3 captured and judged the whole run. So `api_key=`
  followed by `process.env.`, 1100 `A` and `.tail`, and
  `Authorization: Bearer ` followed by `process.env.`, 1100 `A` and `-tail`,
  are `CLEAN` in 2.3.0 and `VIOLATION` in 2.2.3; `api_key=` followed by
  1500 `A` and `=` is `VIOLATION` in 2.3.0 and `CLEAN` in 2.2.3; and
  `Authorization: Bearer ` followed by an OpenAI project key of its prefix and
  1500 `a` is two `CREDENTIAL` findings in 2.3.0 and one in 2.2.3. With 900 in
  place of 1100 and 1500, the two versions agree.
  [docs/detection.md](https://github.com/opena2a-org/aicomply/blob/main/docs/detection.md#regex-layer-always-on)
  states the rule.
- An error the regex engine throws for one pattern no longer ends the scan:
  the other patterns run and their findings stand, the result lists the
  pattern in `unevaluatedPatterns` with a `PATTERN_NOT_EVALUATED:<id>`
  finding, and the verdict is not `CLEAN`. `scanEachPattern()` returns the
  matches and the same list; `scanPatterns()` throws an error that names the
  pattern once every pattern has run.

## Known issues

- **Against the production Registry, only a listed package has a fleet
  anomaly signal** ([#205](https://github.com/opena2a-org/aicomply/issues/205)).
  The production Registry answers the fleet request that names no package,
  the only fleet request 2.2.3 sends, with HTTP 400, so the fleet index does
  not load from it; it answers the request that names a package and its type
  (checked 2026-10-18). 2.3.0 sends that request for each package listed in
  `sourcePackages` or passed to `addSourcePackages()`, and `comply()` sends
  no Registry request (contract AC-005). For a package that is not listed,
  `registrySignals.fleetAnomalyScore` is `null` and the fleet anomaly
  threshold does not apply; without a supply-chain alert its lookup returns
  `error`, and the verdict stays as the classifiers set it. Mitigation: list
  each source package with its type before you classify its input, or pass
  `onRegistryUnknown: 'deny'` (or `'violation'`) so a lookup that returns
  `error` changes the verdict.
