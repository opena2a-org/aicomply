# aicomply 2.3.0

Release notes for `@opena2a/aicomply` 2.3.0, against 2.2.3. The 2.2.3 figures and
outputs below come from the published 2.2.3 package and the 2.3.0 ones from this
tree, both run under Node.js v26.12.0.

## Exit code change: no input exits 2

`aicomply scan` now exits `2` with a `no input` message when the input is 0 bytes.
2.2.3 reported `CLEAN` and exited `0` for the same input.

| Input | 2.2.3 | 2.3.0 |
| --- | --- | --- |
| An empty file | `CLEAN`, exit 0 | `aicomply: no input: <file> is 0 bytes`, exit 2 |
| Empty stdin | `CLEAN`, exit 0 | `aicomply: no input: (stdin) delivered 0 bytes`, exit 2 |
| `git diff --cached` with nothing staged | `CLEAN`, exit 0 | `aicomply: no input: (stdin) delivered 0 bytes`, exit 2 |

A 0-byte file named beside a non-empty one does not decide the exit code: the
result is that of the non-empty file.

A gate written as `scan -q || echo "..."` now takes its failure branch when nothing
is staged. To fail on findings only, test for exit `1`:

```bash
git diff --cached | npx @opena2a/aicomply scan -q; [ $? -eq 1 ] && echo "staged changes not cleared"
```

[docs/commands.md](https://github.com/opena2a-org/aicomply/blob/main/docs/commands.md#exit-codes)
lists the exit codes.

## CLI

- A finding's value is printed as `•••`, with no characters of the detected
  value. 2.2.3 printed `123-•••89` for the SSN `123-45-6789`. The `--json`
  `maskedValue` field changed the same way.
- Each finding is printed with its line and column in the original input
  (`line 1 col 13`).
- `--json` adds `bytes` and `layers` to each source, and `line` and `column` to
  each finding.
- `--` ends the options, so a file name that starts with `-` can follow it.
  2.2.3 stopped with `aicomply: unknown option '--'`.
- Input that starts with a UTF-16 or UTF-32 byte order mark is decoded in that
  encoding. 2.2.3 printed `CLEAN` for a UTF-16LE file and for a UTF-32BE file
  holding an SSN; 2.3.0 prints `VIOLATION` and exits 1 for both.
- A directory argument gets its own message, which names the directory and
  shows a file glob to scan instead. 2.2.3 printed
  `cannot read '<dir>' (check the path)`.
- When files are named and stdin is piped as well, stdin is left unread and a
  line on stderr says so; add `-` to scan stdin beside the files.
- A `CLEAN` result reads `no findings from the layers that ran`, where 2.2.3
  read `safe to forward`.

## Large inputs

| Input | 2.2.3 | 2.3.0 |
| --- | --- | --- |
| 18,500,020 bytes, one SSN and one spaced card number on each line | stopped after 10 minutes without a verdict | `VIOLATION`, exit 1, 1.94 s |
| 81,397,690 bytes of text holding 55 SSN lines | `JavaScript heap out of memory`, exit 134, after 12.31 s at a 4.5 GB peak resident set | `VIOLATION`, exit 1, 2.09 s at a 473 MB peak resident set |

Both files were scanned with `aicomply scan -q` on one shared machine; the times
are single runs.

## Library

- `comply()` accepts `useGuard: false`, which makes no request to the Guard
  daemon address and returns a regex-only result.
- `comply()` accepts `guardOptions.baseUrl` to reach a Guard daemon on another
  address. An address that does not answer falls back to regex-only.
- `onRegistryUnknown: 'violation' | 'deny'` raises the verdict when the Registry
  cannot vouch for `sourcePackage`. With `sourcePackage: 'express'`, no
  `registryCache` and `onRegistryUnknown: 'deny'`, 2.3.0 returns `DENY` with a
  `REGISTRY_UNKNOWN` violation; 2.2.3 does not read the option and returns
  `CLEAN`.
- `registrySignals.status` reports the Registry lookup as `hit`, `miss` or
  `error`.
- The result carries `pack` (the pattern pack's `version` and `sha256`) and
  `layers` (the layers that ran, for example `["normalize", "regex"]`).

## Known issues

- **The supply-chain hard block does not fire**
  ([#205](https://github.com/opena2a-org/aicomply/issues/205)). The Registry
  cache requests `/api/v1/registry/fleet/anomaly-signal` with no package name or
  type; #205 reports that the Registry answers that request with HTTP 400. The
  cache then holds no fleet data, and the lookup for a package returns `error`
  before it reads the supply-chain alert list, so `registrySignals.status` is
  `error` and `supplyChainBlock` is `false`. 2.2.3 has the same request.
  Mitigation: pass `onRegistryUnknown: 'deny'` (or `'violation'`) so a lookup
  that returns `error` changes the verdict. The fix is tracked in #205.
